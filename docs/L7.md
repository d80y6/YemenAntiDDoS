# Layer 7 (L7) Inspection

> العربية: نظرة عامة على الميزات المؤسسية في [docs/ENTERPRISE-UPGRADE-AR.md](ENTERPRISE-UPGRADE-AR.md)


## Overview

YemenAntiDDoS inspects application-layer traffic on captured payloads to detect and surface
HTTP floods, Slowloris connections, and TLS ClientHello bursts. Parsing runs on the Node
using `shared/l7` and results are aggregated in-memory per destination, then pushed to the
Controller via the existing `CriticalEventStream` as `pb.CriticalEvent` messages.

## Node Configuration

Add an `l7` block to the Node configuration. L7 parsing requires the first ~512 bytes of each
TCP payload, so ensure `sample_bytes` is set to at least 512 on every XDP interface. The value
is accepted anywhere in `128-512` (default `256`); with `l7.enabled: true` and a smaller window
the Node logs `WARN l7: sample_bytes=<n> may truncate TLS ClientHello` at startup rather than
failing, so HTTP/Slowloris detection still works but ClientHello parsing is incomplete.

Keys and defaults (`*` = the value shown is set explicitly here, `D` = code default):

```yaml
l7:
  enabled: false              # D false
  window_seconds: 1           # aggregation window
  http_rps: 1000             # * HTTP requests/s per destination
  tls_hsps: 500              # * ClientHellos/s per destination
  slowloris_conns: 50        # * slow-open connections per destination
  max_tracked_destinations: 4096   # destinations tracked per window
  max_tracked_flows: 65536          # D 65536 — slow-open connections kept (Slowloris)
  max_open_fragments: 256          # D 20 — reassembly slots
  sample_bytes: 512                # per-interface window, 128-512
```

## Data Flow

1. Packets captured by the XDP datapath are sampled/parsed.
2. `l7collector.Collector` tracks HTTP requests, Slowloris connection patterns, and TLS
   ClientHello handshakes per destination IP within sliding windows.
3. Events are emitted **only when a threshold is crossed** (`http_rps`, `tls_hsps` or
   `slowloris_conns`): a single benign ClientHello or request below threshold never reaches
   the Controller. Fingerprint (JA3/JA4) and User-Agent distributions ride along on the event
   that does cross. The wire event type is the collector's (`http_flood`, `tls_anomaly`,
   `slowloris`); the store maps them to the `l7_http_flood` / `l7_tls_anomaly` /
   `l7_slowloris` kinds.
4. The Controller receives these events via gRPC `CriticalEventStream` and feeds them into
   `controller/internal/l7store` for real-time aggregation and querying. The store ignores
   non-L7 event types, so L3 critical events (`burst_emergency`, `hard_threshold_exceeded`,
   `syn_flood`, ...) never pollute the L7 read model.

### Counter keys

Flat counter keys on the event wire are shared constants in `shared/l7/keys.go`
(`http_requests`, `tls_handshakes`, `tls_sni_missing`, `slowloris_conns`,
`slowloris_sources`, `unique_sources`, ...). The Node collector emits them and the
Controller's `l7store` parses them, so a rename cannot silently zero a Console field.

### Slowloris

Slowloris detection accumulates **raw payload fragments per 5-tuple**, not request
lines: a byte-drip client that never forms a request line is still counted, and a
sustained attack re-flags in every aggregation window instead of going silent after
its first flag.

### Fingerprints

JA4 is the canonical encoding: 4-character lowercase hex digests over sorted hex
ciphers and extensions (SNI/ALPN excluded) plus a fourth segment hashing
signature_algorithms in wire order, version taken from `supported_versions`, and
marker `i` when the SNI is absent or an IP literal. JA3 keeps the Salesforce
pre-hash + MD5 form.

### Anti-bot challenge

When `af_xdp` is enabled, challenged HTTP traffic is answered by the Node's
JS-PoW responder: an unsolved request gets an `HTTP 307` carrying a signed token
(and the original target as `n`), the challenge page embeds that token and its
solved navigation resubmits `t=` + `xsight_pow=`, and the Node verifies
`sha256(ASCII token || ASCII nonceHex)` — the exact bytes the page's WebCrypto
digest hashes — before admitting the client into `validated_clients`. Tokens are
single-use.

## Console

The **L7** dashboard (`/l7`) displays:
- KPI cards for HTTP floods, Slowloris, and TLS ClientHello
- Stacked-bar chart of events over time (width measured via ResizeObserver)
- Top destinations and sources
- Reporting nodes
- Top JA3 / JA4 fingerprints and User-Agents
- Recent events table with type pill, destination, details, and counts

## API Endpoints

| Endpoint | Description |
|----------|-------------|
| `GET /api/l7/summary?window_minutes=1..240` | Aggregated L7 statistics, time series, top targets/sources, and recent events |
| `GET /api/l7/events?limit=1..1000` | Recent L7 events in newest-first order |

## Notes

- L7 aggregation is in-memory on the Controller (no database persistence) for low-latency
  real-time dashboards.
- The Node aggregates over windows and emits events to the Controller; the Controller
  maintains its own bounded store (`l7store`) with ring buffers and time-based pruning.
- L7 events share `CriticalEventStream` with L3 alerts; the stream is a bounded
  (drop-oldest) queue per Node so a stalled handler never blocks receipt.
